# devops-mcp-server

MCP (Model Context Protocol) server exposing DevOps tools (Kubernetes, Prometheus,
Alertmanager, Loki, Tracing) consumed by `devops-ai-agent`. Part of a 3-repo system: `devops-ai-agent`,
`devops-mcp-server` (this), `llm-worker`.

**Read `MEMORY_BANK.md` before adding tools or touching transport/auth** — it holds the
architecture and design decisions.

## Commands
- Build: `npm run build` (tsc → `dist/`)
- Test: `npm test` (`node:test` + tsx, zero extra deps)
- Dev: `npm run dev`
- **Node 24 required.** Default shell node is v14 — use `~/.nvm/versions/node/v24.16.0/bin` on the PATH.

## Conventions
- TypeScript ESM (NodeNext). Test files `*.test.ts` excluded from the build.
- Tools live in `src/tools/<domain>/`; register by adding to the spread in `src/tools/index.ts`.

## Gotchas (see MEMORY_BANK.md for the full list)
- **Tools are auto-discovered** by the agent via `listTools()` — adding a server-side tool needs **no agent change**. Conversely, the agent caches the tool list at startup, so a tool that's listed but fails on call makes the LLM loop (relevant for any future gated/write tools: register conditionally, don't just guard the handler).
- **HTTP mode is stateless:** a fresh `McpServer` is created per `/mcp` request.
- **Auth:** `/mcp` requires `Authorization: Bearer <MCP_AUTH_TOKEN>` when set (constant-time check); `/health` stays open for probes. Unset token in http mode logs a warning — never silently open.
- **Tracing backends:** Tempo or Jaeger only (adapters in `src/tools/tracing/adapters.ts`). OTel Collector is ingest-only — not a query backend.
- **`flux_reconcile`** is the one write tool the GitOps guard does not refuse — it restores the repo's declared state instead of introducing new state. Its namespace guard runs on the **workload's** namespace (the HelmRelease usually lives in the permanently-blocked `flux-system`), and the target release is derived from the workload's Flux labels, never named by the caller. Needs `patch` on `helmreleases` — **granted in the dev overlay only**.
- **"What is firing" is an Alertmanager question, never a Prometheus one.** `alertmanager_get_alerts` (`/api/v2/alerts/groups`) replaced `prometheus_get_alerts`, which is deleted: `/api/v1/alerts` only sees rules Prometheus itself evaluates, so adding a second evaluator (Loki Ruler, Kibana) would silently turn it into a partial view answering "nothing else is firing" while a log-based alert pages. Corollary rules: **suppression is a label, not a filter** — `silenced`/`inhibited` alerts come back labelled, because a silenced alert is still firing and dropping it would read as recovery (the agent's post-remediation `alertState()` depends on this); and the `summary` counts are never capped even when the per-group detail is (`MAX_DETAIL_ALERTS`), same reasoning as `k8s_cluster_health`. Alerts still `pending` in an evaluator are deliberately invisible — nothing has been routed yet.
- **`conciseCause()` handles axios errors** (`err.response.data`), not just K8s `ApiException`. Prometheus/Loki/tracing failures otherwise reach the model as a bare `Request failed with status code 400`, and it retries the same broken query.
- **Three filters stand between `k8s_find_unused_resources` and a wrong delete, and they catch different things.** (1) The reference index reads running pods *and* every workload pod template — pods alone call a scaled-to-zero Deployment's ConfigMaps garbage. (2) An `ownerReference` drops the object for free (no extra API call, the field was in the list response already): its controller owns its lifecycle and the GC handles it. That covers operator-**created** objects. (3) Every surviving ConfigMap/Secret/PVC/ServiceAccount is matched against every string in every custom resource in the cluster — that covers operator-**referenced** ones, which carry no ownerReference and no pod reference. Matching is bare string equality on keys and leaves because an operator's schema is its own (`spec.configMapRef.name`, `spec.tls.secretName`, …) and cannot be enumerated; a coincidental match keeps something unused, a missed one deletes something live. Needs `rbac.readAllCustomResources` (chart 0.3.0+); without it `crossCheck.crdsUnreadable` fills up and the tool downgrades its own note.
- **An optional string parameter must accept `""` as "omitted" — use `blankToUndefined()` from `kubernetes/schemas.ts`.** `""` is how a model spells "not applicable" in a required-shaped slot; a schema that rejects it is technically right and practically a bug. Found live: `k8s_find_unused_resources` got `{"namespace":""}` meaning the whole cluster and returned a ZodError. It recovered by retrying without the field, so the cost looked like one wasted round — but the same input reaches `k8s_cluster_health`, the tool the system prompt names FIRST for every cluster-wide question, where a model that does not work out the fix loops instead. Whitespace is NOT blank: that is a typo, and swallowing it hides one.
- **`k8s_correlate_pods` answers "one cause or many" with set algebra, not with the model's memory.** Several broken pods used to mean `k8s_describe_pod` per pod and a spec diff done in the model's head, which it does badly — the benchmark's eight-pods-one-cause case failed every attempt, never naming the env var the pods shared. The tool flattens each pod into `kind=value` facts (node, image, ConfigMap/Secret/PVC refs, ServiceAccount, env variable NAMES — never values, which can be credentials) and intersects them. The payload is `uniqueToBroken`: shared by the failing set and held by NO healthy pod in the namespace. `sharedWithHealthy` is noise, since pods of one Deployment share nearly everything. **`healthy.length === 0` is checked before `unique.length > 0`** — with no control group every shared attribute is vacuously unique, and reporting that list reads as a finding. Reference walking is `kubernetes/podspec.ts`, shared with the unused scan; one walker, because missing a reference is what makes the unused scan recommend deleting live config.
- **Every unused finding carries `managedBy`, and it decides what to DO about it.** `flux` (the `kustomize.toolkit.fluxcd.io/name` label) or `helm` (the `meta.helm.sh/release-name` annotation) means something DECLARES that object: deleting it through the API is a no-op Flux undoes on the next reconcile, so the durable removal is a PR — and it is evidence the finding is a false positive, because the scan's blind spots are exactly where someone declares a thing no workload mounts. `none` is the only genuine orphan shape. Both markers were already in the list response, so this costs no extra API call; `provenance.declaredInGit`/`.undeclared` promote the split out of the rows so it cannot be missed.
- **`k8s_recommend_resources` returns `idleWorkloads`, and it is the ONLY input the agent's scale-to-zero quarantine accepts.** It exists because nothing here could name a workload worth quarantining — the unused scan's workload finding is `replicas === 0`, i.e. already quarantined. Deliberately CPU-only: the stronger-sounding alternative (join `http_server_requests_total`, require a zero request rate) guesses its join, because that metric's label is the app's own `service` name, and returns an empty vector for an uninstrumented workload — indistinguishable from no traffic, and here that empty result would resolve as "take it offline". Probes cost CPU, so a probed pod is never at literal zero. What CPU alone misses is a scheduled burst, which is why the flag is refused below `IDLE_MIN_WINDOW_HOURS` (24) and why `IdleWorkload` reports `cpuP95Below` — the bound — rather than `observed.cpuP95`, which `fmtCpu` floors at `10m` and would print next to a claim of "under 2m". The roll-up demands EVERY container be measured and idle: a half-measured workload is refused, because the unmeasured container is where the traffic would show. **`idleWorkloads` is the LAST key in the response on purpose** — the agent drops the middle of any tool result over 8000 chars, and this response passes that on any real cluster, so in the middle it would have been silently cut and the agent's fail-closed gate would have refused every quarantine.
- **`k8s_scale` refuses zero unless `quarantine: true`.** The exception exists because removing a workload that "looks unused" is irreversible against a cluster with no backups, while scaling it to zero is one action to undo — so the reversible answer is the one that gets a path. Opt-in at the call site, never inferred from `replicas === 0`, so "take this offline" can never be the accidental reading of a number; it relaxes nothing else (namespace allowlist, `MAX_SCALE_DELTA`, dry-run, GitOps verdict and the human click all still run, and a Flux-managed workload still routes to a PR rather than a patch Flux would revert). This server cannot verify the idle evidence — it has no thread — which is exactly why the flag is explicit and shows up in the approval card.
- **`k8s_delete_orphan` is the one tool here whose mistake cannot be undone from the cluster, so every guard is code and none is a prompt rule.** It takes ConfigMap/Service/ServiceAccount and Deployment/StatefulSet **already at 0 replicas** — the kinds a stored manifest fully restores. It refuses when anything declares the object (`managedBy !== "none"`: Flux restores it anyway, and something declaring it on purpose is evidence the finding is wrong), when an `ownerReference` explains it, when a workload still runs replicas, when it is younger than `MIN_ORPHAN_AGE_DAYS` (env, **default 14** — new is not abandoned; configurable only because the benchmark cannot age a fixture, Kubernetes owning `creationTimestamp`, and **a value under 14 is warned about on every boot** — the bench and production share one server, so a floor lowered for a run stays lowered until somebody restores it), when `creationTimestamp` is missing (age is the only abandonment evidence available, so no age means no delete), and always for `default/kubernetes`. `orphanRefusal()` is pure and exported because each branch is a live object that survives if the check is right. The manifest is captured by `restorableManifest()` **immediately before** the delete, not at proposal time — the object can change between a card being posted and someone clicking Approve — and stripped of `uid`/`resourceVersion`/`generation`/`managedFields`/`status`/`last-applied-configuration` plus a Service's allocated `clusterIP`, because one leftover field makes the restore fail at the worst possible moment. **Secrets and PVCs are excluded permanently, not pending:** a Secret's backup is its credentials, and a PVC's manifest is not its data.
- **`orphanKeys` is the LAST key of the unused-scan response, same reason as `idleWorkloads`.** It lists `namespace/kind/name` for findings nothing declares — the deletable set, and the only thing the agent may propose `k8s_delete_orphan` against. `findings` is the bulk of that response, so a key buried in a row would be cut by the agent's middle-dropping compaction on exactly the clusters worth cleaning, and the agent's gate fails closed: the capability would look present and never fire.
- **`kubernetes/provenance.ts` is shared between the scan that REPORTS provenance and the tool that REFUSES without it.** Same reason `podspec.ts` is shared: two copies drift, and the direction they drift in is "the reporting side says nothing declares this, the deleting side agrees, and Flux had a label neither of them read".
- **`k8s_find_unused_resources` is a REVIEW list, never a delete list.** A false "unused" is a delete recommendation for something live, so its reference index reads running pods *and* every workload pod template (pods alone call a scaled-to-zero Deployment's ConfigMaps garbage), skips objects that are unreferenced by construction (`helm.sh/release.v1`, SA tokens, `kube-root-ca.crt`, `default` SA, `ExternalName` Services), and pages via `listAll()` — truncation here does not mean fewer findings, it means a live object reported as orphaned.
- **`k8s_recommend_resources` joins K8s + Prometheus server-side on purpose.** Three model-written calls (subquery PromQL, `512Mi` parsing, pod→Deployment mapping) is three chances to be confidently wrong about a number that lands in an RCA. It is a percentile heuristic and its `method` field says so; a CPU limit is only ever raised, never introduced. `namespace`/`workload`/`window` are regex-validated because they are interpolated into PromQL.
- **`k8s_cluster_health` must never inherit `config.k8sListLimit`.** Every other list tool is per-namespace and capped; this one is the cluster-wide *scan*, so a cap would turn a complete answer back into a partial one that still reads as complete — the exact bug it was built to kill (the agent once said "all healthy" after seeing 6 of 20 namespaces). It pages via `_continue` and reports `scanned.complete:false` if it ever hits its own ceiling. Judge pods on **readiness, not phase** — a CrashLoopBackOff pod's phase is `Running`.
